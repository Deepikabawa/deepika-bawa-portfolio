Once the module skeleton is in place, the real work starts: getting source data into JSON, mapping it onto the right Drupal fields, and pulling media in from Azure Blob Storage instead of copying files by hand. This is roughly the pattern I use for that.

Step 1 — Export the source data as JSON

Wherever the content is coming from, export it to JSON and land it somewhere the migration can reach — a public path, or a container in Azure Blob Storage. Keep the shape predictable: one array of items, each with a stable id.

{
  "items": [
    {
      "id": "1024",
      "title": "Our Approach to Formulation Chemistry",
      "body": "<p>How we test and validate new formulations.</p>",
      "image_url": "https://mystorage.blob.core.windows.net/media/formulation-hero.jpg",
      "tags": ["chemistry", "formulation"]
    }
  ]
}

Step 2 — Set up the destination fields in Drupal

Before any mapping happens, the destination content type needs somewhere to put each piece of data. For the JSON above, that's a body field (core), a media reference field for the hero image, and a taxonomy reference field for tags — created through Manage Fields, or as config:

field_name: field_hero_media
entity_type: node
type: entity_reference
settings:
  target_type: media
cardinality: 1

Step 3 — Point the migration at the JSON source

Migrate Plus's url source plugin, with a JSON data parser, reads the file directly — no custom source plugin needed for a straightforward feed:

source:
  plugin: url
  data_fetcher_plugin: http
  data_parser_plugin: json
  urls:
    - 'https://mystorage.blob.core.windows.net/media/articles.json'
  item_selector: items
  fields:
    - name: id
      selector: id
    - name: title
      selector: title
    - name: body
      selector: body
    - name: image_url
      selector: image_url
    - name: tags
      selector: tags
  ids:
    id:
      type: string

Step 4 — Map the fields

With the source fields named, the process pipeline maps each one onto its Drupal field. Tags go through sub_process so each array value becomes its own taxonomy term, created on the fly if it doesn't exist yet:

process:
  title: title
  body/value: body
  body/format:
    plugin: default_value
    default_value: basic_html
  field_tags:
    plugin: sub_process
    source: tags
    process:
      target_id:
        plugin: entity_generate
        entity_type: taxonomy_term
        value_key: name
        bundle_key: vid
        bundle: tags
  field_hero_media/target_id:
    plugin: azure_blob_media_import
    source: image_url

Step 5 — Pull media in from Azure Blob Storage

azure_blob_media_import is a small custom process plugin: it downloads the file from its blob URL, saves it into Drupal's file system, and wraps it in a Media entity so the rest of the site can reference it normally.

<?php

namespace Drupal\my_migration\Plugin\migrate\process;

use Drupal\migrate\ProcessPluginBase;
use Drupal\migrate\MigrateExecutableInterface;
use Drupal\migrate\Row;
use Drupal\file\Entity\File;
use Drupal\media\Entity\Media;
use Drupal\Core\File\FileSystemInterface;

/**
 * @MigrateProcessPlugin(
 *   id = "azure_blob_media_import"
 * )
 */
class AzureBlobMediaImport extends ProcessPluginBase {

  public function transform($value, MigrateExecutableInterface $migrate_executable, Row $row, $destination_property) {
    if (empty($value)) {
      return NULL;
    }

    $data = file_get_contents($value);
    if ($data === FALSE) {
      return NULL;
    }

    $filename = basename(parse_url($value, PHP_URL_PATH));
    \Drupal::service('file_system')->prepareDirectory(
      'public://migrated',
      FileSystemInterface::CREATE_DIRECTORY
    );

    $file = File::create(['uri' => 'public://migrated/' . $filename]);
    file_put_contents($file->getFileUri(), $data);
    $file->setPermanent();
    $file->save();

    $media = Media::create([
      'bundle' => 'image',
      'field_media_image' => [
        'target_id' => $file->id(),
        'alt' => $filename,
      ],
      'status' => 1,
    ]);
    $media->save();

    return $media->id();
  }

}

For a large batch, fetch the blobs in a queue or in smaller runs rather than one synchronous download per row, and account for SAS token expiry if the URLs are time-limited.

Step 6 — Run it

drush pm:enable my_migration -y
drush migrate:import my_node_migration

Then check /admin/content/media to confirm the media entities landed correctly, and spot-check a few nodes for the field mapping.

Re-running the migration updates existing rows rather than duplicating them, as long as the source id stays stable — that's what lets you re-import safely after fixing a mapping, instead of rolling back the whole migration each time.

GoTo Webinar is a contributed Drupal module I built to bring GoToWebinar setup, registration, and lifecycle management directly into the CMS.

Why build this

Marketing teams running webinars usually end up split across two systems: GoToWebinar for the event itself, and the CMS for everything around it — landing pages, registration forms, follow-up content. Keeping the two in sync by hand doesn't scale once webinars are a regular part of the marketing calendar. This module exists to close that gap, so webinar setup, registration, and marketing-tool integration can live inside Drupal rather than bolted on beside it.

What it does

  • Webinar setup from Drupal — create and configure webinars against the GoToWebinar API without leaving the CMS.
  • Registration handling — capture and sync registrants through Drupal's own forms and workflows instead of a separate registration page.
  • Lifecycle workflow — each webinar moves through a defined lifecycle (draft, scheduled, live, completed) so editors can see and manage its state directly from the content edit screen.
  • Marketing tool integration — built to sit alongside tools like HubSpot, so registrant and webinar data can flow into the rest of the marketing stack.

Where it stands

It's a fresh release under the Integrations category on Drupal.org, GPL-licensed like any contributed module. The project page and issue queue are open for anyone who wants to try it, file an issue, or contribute — the source is on GitLab if you want to see how it's put together before installing it anywhere.

Most Drupal performance problems come down to a handful of repeat offenders: pages doing more work than they need to, a database answering the same questions over and over, and assets that are bigger or more numerous than they should be. Here's where I look first, in order.

1. Turn on the caching Drupal already gives you

Before reaching for anything external, make sure core's own caching is actually working. For anonymous traffic, Internal Page Cache serves whole pages straight from cache. For authenticated or personalized pages, Dynamic Page Cache caches everything except the parts that genuinely vary per user, and BigPipe streams those personalized fragments in after the cached shell, so a logged-in user still gets a fast first paint.

drush pm:enable page_cache dynamic_page_cache big_pipe -y

These three cost nothing to enable and quietly fix a large share of "why is this page slow" complaints on their own.

2. Move cache and session storage off the database

By default, Drupal's cache bins live in the database — fine for small sites, a bottleneck once traffic grows. Moving cache (and ideally sessions) to Redis or Memcache takes that load off MySQL entirely:

$settings['cache']['default'] = 'cache.backend.redis';
$settings['redis.connection']['host'] = '127.0.0.1';
$settings['redis.connection']['port'] = 6379;

On Acquia or Pantheon this is usually a flag or a service already provisioned for you — check the platform docs before rolling your own.

3. Find the slow queries before guessing

Don't optimize blind. Devel's query log and the Fast 404 pattern catch a lot, but for anything beyond a quick check, turn on MySQL's slow query log and look at what's actually running long:

SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;

In my experience the usual culprits are missing indexes on custom field tables, Views without proper caching, and entity loads happening in a loop instead of a single multiple-load. Views has its own query and render caching settings — for anything that isn't time-sensitive, "Time-based" caching set to an hour or more removes a huge amount of repeat query work for free.

4. Offload search instead of querying it

If a site does any non-trivial searching or filtering, running it through Drupal's own database queries scales badly. Handing that off to Elasticsearch via Search API keeps expensive filtering and full-text search off the primary database and off the request/response cycle entirely.

5. Get assets under control

  • CSS/JS aggregation and compression — on in production, always. Combined with HTTP/2, this matters less than it used to, but it's still free performance left on the table if it's off.
  • Responsive images — use image styles and the Responsive Image module rather than shipping one large image to every device.
  • WebP — serve WebP derivatives where the browser supports it; noticeably smaller than JPEG/PNG at the same visual quality.
  • Lazy loading — Drupal 9.3+ lazy-loads images below the fold by default; verify it's actually enabled on the theme's image output.

6. Put a CDN and reverse proxy in front

A CDN for static assets and images, plus a reverse proxy like Varnish (or the platform's built-in edge cache on Acquia/Pantheon) in front of Drupal, means most anonymous requests never reach PHP at all. This is usually the single biggest win for public-facing pages, and it's mostly configuration rather than code.

7. Keep watching after launch

Performance work doesn't end at deployment. Tools like Datadog or New Relic APM show exactly which requests are slow, which queries dominate response time, and whether a deploy quietly regressed something. I'd rather catch a slow endpoint from a dashboard than from a client's email.
